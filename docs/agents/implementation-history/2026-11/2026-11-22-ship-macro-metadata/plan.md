## Prior Project Context
The ledger holds no strategic vision and no prior projects for x4-core, and no stored insight applies to this work. The most recent release is v1.4.1 (cross-folder macro fix, already out); this plan builds on its cross-folder-capable `MacroFileDefs::getByMacroName()` and its storage macro resolution. The first consumer is the sibling repository `x4-mod-cargo-sizes`, which currently parses raw extracted XML (`src/Mods/CargoSizesMod/Build/CargoSizeExtractor.php`, `XML/ShipXMLFile.php`, `XML/ShipXML/SteeringCurve.php`, `Output/Physics/AccelerationOverrideDef.php`); its migration to x4-core is a separate, later plan and is not part of this one.

## Summary
Make x4-core's ship and ware data complete enough that consumers no longer need to read raw game XML. The plan has four parts:

1. **Ship macro links.** The four facts the Cargo Sizes mod needs: the ship's own macro name, its storage macro name, whether its own macro file has an explicit `<accfactors>` element, and its alias target.
2. **Ship macro properties.** The remaining useful ship macro data: steering curve, explosion damage, purpose, drone, deployable and countermeasure capacity, hangar capacity per dock size, thruster size, default and compatible software, icon, base and variation names, secrecy level, travel drive stability, gas gather rate, radar range, equipment modifiers, capturability, prestige, boost timing, threat score, the player-coverable ownership flag and the built-in default loadout.
3. **Ware data.** Price, production recipes, licence, description, illegal-for factions, the buy restriction flag, cargo volume and transport type for every ware, plus a new production methods collection (`data/production-methods.json`) that gives production method IDs a label, tags and default races. Volume and transport type make `cargoCapacity` usable: `ShipDef` gains `canTransport()` and `getCargoUnits()` (how many units of a ware fit). This also fixes the wares extractor so it applies DLC `<add sel="/wares/ware[@id]">` patches, which it currently ignores. That bug leaves 195 wares (14 of them ships) missing owner factions, and drops the DLC production methods. `WareDef` keeps its price and production data as raw records and builds the value objects on first access, because `WareDefs` is loaded by every domain.
4. **Finders and consumer helpers.** Cheap filters on the existing finders (`WareFinder::selectProducedBy()`, `selectUsingResource()`, `selectLicence()`, `selectIllegalFor()`, `selectTransportType()`; `ShipFinder::selectPurpose()`, `selectThrusterSize()`, `selectCapturable()`, `selectWithHangar()`, `selectWithSoftware()`), a production cost helper (`WareProduction::getResourceCost()`), and an English fallback for translatable text (`Language::tsWithFallback()`), so a language that lacks an entry never leaks a raw `{page,id}` code.

All public API changes are additive. New ship data is grouped in a new `ShipMacroProperties` value object, which `ShipDef` receives as a single trailing optional constructor parameter. `data/wares.json` and `data/ships.json` are regenerated and `data/production-methods.json` is new. The only pre-existing values that change are the corrected `factions` (wares) and `usedBy` (ships) lists, and a baseline diff verifies this. It ships as the next minor version (v1.5.0), tracked in a WIP changelog section.

## Architectural Context
- `src/X4/Database/Ships/ShipsExtractor.php` (680 lines) builds ships from the ware definitions (`WareDefs`). It loads each ship macro through `MacroFileDefs::getInstance()->getByMacroName($def->getMacroID(), $def->getDataSourceID())` and resolves an optional alias macro (`resolveParentMacro()`). Stats are read from the own DOM first, then the alias DOM (`resolvePropertyAttribute()`, `resolveJerkAttribute()`). Cargo is resolved through `resolveStorageCapacity()` → `findStorageInDOM()` → `extractCargoFromStorageMacro()`, which discards the storage macro name. Dock sizes come from `extractDockSizesFromShipMacro()` / `extractDockSizeFromMacro()`. `usedBy` is copied from `WareDef::getFactionIDs()`.
- `src/X4/Database/Ships/ShipDef.php` is the immutable ship item. It has `KEY_*` constants, a positional constructor of 42 parameters, `fromArray()` (via `ArrayDataCollection`), `toArray()` and typed getters. It inherits `getWare()` from `CollectionItemTrait`. `data/ships.json` (256 ships) is its store.
- `src/X4/Database/Ships/Equipment/ShipSlotDefinition.php` is the existing pattern for a small nested ship value with `fromArray()`.
- `src/X4/Database/Modules/ModuleMacroExtractor.php` is the existing pattern for a per-item macro reader that a collection extractor calls (`ModuleExtractor` L51).
- `src/X4/Database/Ships/ShipFinder.php` filters by builder faction, class and size. `ShipSizes` defines `xs, s, m, l, xl`.
- `src/X4/Database/Wares/WaresExtractor.php` reads every data folder's `libraries/wares.xml` with `byTagName('ware')`. DLC files are `<diff>` documents, so the extractor picks up the full ware definitions they add but ignores the 773 `<add sel="/wares/ware[@id='X']">` patches (owners, productions, `illegal`). It is declared in the misspelled namespace `Mistral\X4\Database\Wares`.
- `src/X4/Database/Wares/WareDef.php` has a positional constructor of 10 parameters and omits optional keys from `toArray()` when they are empty.
- `src/X4/Database/MacroIndex/MacroFileDef.php` / `MacroFileDefs.php` plus `data/macro-index.json` map macro names to files, falling back across data folders case-insensitively.
- Translations: `Languages::getInstance()->getEnglish()` and `Language::ts('{page,id}')`; `data/lang-*.json` ships 7 languages. `TranslationDefs::t()` (`src/X4/Database/Translations/TranslationDefs.php` L59) returns the raw code `{page,id}` when a language lacks the entry; there is no way to ask whether an entry exists. Every ware description (1760 distinct codes) and ship name code (125 base names, 12 variations, 12 short variations) is present in all 7 shipped language files today, so a fallback is defensive (game updates, trimmed language files) rather than fixing a current gap.
- `src/X4/Database/Wares/WareDefs.php::registerItems()` builds every `WareDef` (1869) through `WareDef::fromArray()` on first use, and `WareDefs` is reached from every domain through `getWare()`, `findByMacro()` and the macro index. Anything `fromArray()` builds eagerly is paid by all consumers. In the extracted data there are 1695 `<production>` entries on 1305 wares (4909 resource lines).
- `src/X4/Database/Wares/WareFinder.php` only offers `selectTag()` (all selected tags must match), `selectGroup()` (any selected group), data source and label filters. `src/X4/Database/Ships/ShipFinder.php` offers builder faction (any), class (any) and size (any); each `select*` method resolves a string or object through the matching collection, which throws for an unknown ID.
- `ShipDef::getCargoType()` returns the raw `<cargo tags>` attribute of the storage macro, a space-separated list (`container`, `solid`, `liquid`, `condensate`; `none` when there is no hold). Ships.json holds eight distinct values, e.g. `container solid liquid` on 3 ships.
- Licences: no `libraries/licences.xml` exists in any data folder. A ware's `<restriction licence="…">` names a licence type (16 distinct types on the 1083 licensed wares in `wares.json`, 17 including excluded wares) that is defined only per faction in `libraries/factions.xml` (`<licences><licence type name minrelation price precursor …>`, 460 elements over 24 types, vanilla plus DLC `<add>` patches). The `name` text codes differ per faction and tier (about 20 distinct codes per type), so no licence has one canonical label.
- Extractor tests (`WaresExtractorTests::test_extract`, `ShipsExtractorTests::test_extract`) run the extractors, so `composer test` rewrites `data/wares.json` and `data/ships.json`.
- Verified game-data facts (v9.0.0.0) are in `research-brief.md`. The ones this plan depends on are repeated in the steps and the verification oracle.

## Approach / Architecture

### Part A — Ship macro links (unchanged from the previous revision)

| JSON key (`ShipDef::KEY_*`) | Accessor on `ShipDef` | Meaning | Serialization |
|---|---|---|---|
| `macroID` | `getMacroID(): string`, `getMacro(): MacroFileDef` | The ship's own macro name, from `WareDef::getMacroID()`. Never derived from the ware ID. | Always written. |
| `cargoMacroID` | `getCargoMacroID(): ?string`, `hasCargoMacro(): bool`, `getCargoMacro(): ?MacroFileDef` | Canonical name of the storage macro that supplied `cargoCapacity`/`cargoType`: own `con_storage*` connection first, alias target second. | Omitted when null. |
| `aliasMacroID` | `getAliasMacroID(): ?string`, `isAliasMacro(): bool` | The `alias=` target of the ship's own macro. | Omitted when null. |
| `hasOwnAccFactors` | `hasOwnAccFactors(): bool` | True when the ship's own macro file contains an `<accfactors>` element. Partial elements count; the alias target is never inspected. | Always written. |

### Part B — Ship macro properties
Unless a row says otherwise, values are read from the ship's own macro first and from the alias target second, the same rule as the existing stats. Part B accessors live only on `ShipMacroProperties` and are reached through `ShipDef::getMacroProperties()` (e.g. `$ship->getMacroProperties()->getHangar()`); `ShipDef` itself gets no delegators for them (see Considered Alternatives).

|---|---|---|---|---|
| `steeringCurve` | `[{position, value}]` | `getSteeringCurve(): ShipSteeringCurve` | `<steeringcurve><point>` in document order. Point names `position`/`value` are kept from the game because their exact in-game meaning is not documented in the data; the PHPDoc says so rather than guessing. The class is a plain point container (as the mod's `SteeringCurve` is); it does not interpolate, because the interpolation semantics are unconfirmed. | Always written (empty list when absent). |
| `explosionDamageHull`, `explosionDamageShield`, `explosionShieldDisruption` | float | `getExplosionDamage(): ?ShipExplosionDamage` (null when all three are absent) | `<explosiondamage value shield shielddisruption>`. | `thrusterSize` | `xs\|s\|m\|l\|xl` | `getThrusterSizeID(): string`, `getThrusterSize(): ShipSize` | `<thruster tags>`: small→s, medium→m, large→l, extralarge→xl. | Always written. |

| `defaultLoadout` | `[{type, macroID, count, optional}]` | `getDefaultLoadout(): ?ShipLoadout`, `hasDefaultLoadout(): bool` | `<loadouts><loadout id="default">` (own, else alias), flattened into one list of what gets installed. The game splits it into `<macros>`, `<groups>`, `<software>`, `<virtualmacros>` and `<ammunition>` and addresses equipment by macro and connection path. Here each entry has a normalized `type` (`engine`, `shield`, `weapon`, `turret`, `thruster`, `software`, `ammunition`), the `macroID` (for software entries, the software ware ID), a `count`, and `optional`. Identical entries are merged by summing their counts (a turret group's `exact`, an ammunition entry's `max`). Connection paths and group names are game-internal and are deliberately dropped; a future loadout-rules plan that needs them would read the macro directly. The JSON stays flat for scalars and nested only for structured values, like the existing `slots` and `equipment`. In PHP, all Part A and Part B values live in one new immutable value object, `ShipMacroProperties`. Its readonly promoted constructor properties all have defaults, and it has `fromArray(array $shipRecord)` and `toArray()`. `ShipDef` receives it as one trailing optional constructor parameter, `?ShipMacroProperties $macroProperties = null` (null becomes an empty instance). `ShipDef::fromArray()` / `toArray()` delegate to it. `ShipDef` gets `getMacroProperties()` plus delegators only for the Part A facts, the ware data and the three cargo helpers (a named consumer exists for each); all other Part B accessors exist once, on `ShipMacroProperties`, following the sub-object precedent of `getWare()`. Future macro data is added to `ShipMacroProperties`, so `ShipDef`'s positional constructor stops growing.

Parsing moves out of `ShipsExtractor` into a new per-ship reader, `ShipMacroPropertiesExtractor`, following `ModuleMacroExtractor`. A new `ShipMacroConnectionResolver` implements the "connection → child `<macro ref>` → resolved `MacroFileDef`" walk once. Storage, dock sizes and hangar resolution all use it; today that loop is written out twice in `ShipsExtractor` and would otherwise get a third copy.

**Production methods (new collection):** `ProductionMethodDef` / `ProductionMethodDefs` in a new `src/X4/Database/ProductionMethods/` domain, following the data-backed `FactionDefs` collection. Each record has `id`, `label` (English, like other collection labels), `tags` (e.g. `noplayerbuild`, `recycling`) and `defaultRaceIDs`. `isPlayerBuildable()` is derived from the `noplayerbuild` tag. A new `ProductionMethodsExtractor` reads vanilla `<wares><production><method>` and DLC `<add sel="/wares/production">` through `WaresPatchReader`, and writes `data/production-methods.json`. It is exposed as `DatabaseBuilder::extractProductionMethods()` / `composer extract-production-methods` and runs before the wares in `build()`. `WareProduction::getMethod(): ?ProductionMethodDef` links the two.

Ware-level data is not copied into `ships.json`; `wares.json` stays its single source. For direct access, `ShipDef` gets delegating accessors `getPrice()`, `getProductions()`, `getLicenceID()`, `getDescription(?Language)` and `getIllegalFactionIDs()`, which call `getWare()`. `ShipDef` already exposes the ware's label and owners the same way. The other ware-backed domains (`EngineDef`, `ShieldDef`, `WeaponDef`, modules, …) get no such delegators: they already inherit `getWare()` from `CollectionItemTrait`, so their prices are reached as `$engine->getWare()->getPrice()`. The handbook states this, so nobody requests per-domain delegators; the ship delegators exist only because ships are the most-queried domain and already delegate label and owners.

**Cargo helpers (named consumer: the Cargo Sizes mod, plus any fleet or trade tooling).** The ship's `cargoType` and a ware's `transportTypeID` use the same four cargo words. Verified in the data: every token in `ships.json` `cargoType` (`container`, `solid`, `liquid`, `condensate`, with `none` meaning no hold) is also a `transport` value of at least one ware; the ware side additionally has six non-cargo values (`inventory`, `equipment`, `ship`, `research`, `software`, `passenger`) that no ship hold lists. The vocabularies are therefore compatible, but they are not the same set, and `cargoType` is a space-separated list of tokens while `transport` is a single value. `ShipDef` gets:
- `getCargoTypeIDs(): string[]`: the `cargoType` tokens (empty for `none`).
- `canTransport(WareDef $ware): bool`: true when the ware's `transportTypeID` is one of the ship's cargo type tokens. The rule is derived from the matching vocabularies; the game data does not state it, and the PHPDoc says so. It knows nothing about trade rules (station modules are `container` wares too).
- `getCargoUnits(WareDef $ware): int`: `intdiv(cargoCapacity, volume)` when `canTransport()` is true and the volume is positive, otherwise 0.

`WareTransportTypes` (NEW, `src/X4/Database/Wares/WareTransportTypes.php`) is a constants class following `ShipPurposes`: the ten `TRANSPORT_*` constants, `getIDs()`, `getCargoIDs()` (the four cargo types), `idExists()`, `isCargoTypeID()`. Its consumers are extraction-time validation, `ShipDef::getCargoTypeIDs()` and `WareFinder::selectTransportType()`.

**Production cost helper.** `WareProduction::getResourceCost(): ?int` is the sum of `amount × priceAverage` over the production's resources, and `getResourceCostPerUnit(): ?float` divides it by `quantity`. Both return null when a resource is unknown or has no price (none occurs in the data: all 111 resource wares exist and have a `<price>`); a production without resources (20 exist) costs 0. The PHPDoc and handbook state the limits: the basis is the game's reference average price, not a market price; the `effects` (work, sunlight, efficiency) and the production time are not factored in; it is the cost of the inputs, not a profit calculation. Its consumer is production tooling that has to choose between recipes, the same consumer that justifies `ProductionMethodDef`.

**Lazy hydration of ware value objects.** `WareDefs` loads every `WareDef` for all consumers, so `WareDef::fromArray()` must not build `WarePrice` and `WareProduction` objects up front. `WareDef` keeps the raw price record (the three flat keys) and the raw production records (arrays), and builds `WarePrice` / `WareProduction[]` on first access of `getPrice()` / `getProductions()` / `getProduction()`, then caches them in private fields. The constructor accepts either form (`WarePrice|array|null` and a list of `WareProduction|array`) and normalizes objects to records, so direct construction with value objects works and `toArray()` always serializes from the records. `getProductionMethodIDs()`, `getProductionResourceIDs()`, `usesResource()` and `hasPrice()` read the records and never trigger hydration; the finders use them, so a finder scan builds no objects. `ShipMacroProperties` is deliberately not made lazy (see Considered Alternatives).

**Translation fallback.** `Language::tsWithFallback(string $code, ?Language $fallback = null): string` (default fallback: English) returns the text in the language when it has the entry, else the fallback's text, else an empty string; it never returns the raw code. It relies on two new small methods, `TranslationDefs::hasCode(string $code): bool` and `Language::hasCode(string $code): bool`, so "missing" is a real lookup instead of a comparison against the `{page,id}` sentinel. `TranslationDefs::ts()` and `t()` are unchanged. The four accessors that take a `Language` (`WareDef::getDescription()`, `ShipMacroProperties::getBaseName()`, `getVariationName()`, `getShortVariationName()`) use it.

**Patch-aware ware extraction:**
- Pass 1 (as today) collects full ware definitions from every data folder: vanilla `<ware>` elements and DLC `<add sel="/wares"><ware>`.
- `WaresPatchReader` (new) reads the DLC diff files and returns typed `WarePatch` objects (`dataFolderID`, `selector`, `targetWareID` or null, element) for every `<add>`. It has two consumers: the wares pass 2 (ware-targeted patches) and `ProductionMethodsExtractor` (`/wares/production`).
- Pass 2 applies each `<add sel="/wares/ware[@id='X']">`: `<owner>` children are merged into `factions` (sorted, de-duplicated), `<illegal>` children are merged into `illegalFactionIDs`, and `<production>` children are appended to `productions`, in data-folder order.
- Owner and production parsing is shared between both passes, so each is written once.
- Patches that target excluded wares (deprecated or workunit) are skipped with a `NOTICE`. Unknown child elements (none exist today) get a `NOTICE`. `replace`/`remove` operations or any other `sel` form get a `WARNING`, so a future game update cannot silently drop data.
- An unknown faction in a patch skips that owner only, with a `WARNING`. The pass-1 rule that drops a whole ware for an unknown owner stays as it is.
- The extractor moves to the correct `Mistralys\X4\Database\Wares` namespace. A deprecated subclass keeps the old `Mistral\X4\Database\Wares\WaresExtractor` name working.

### Part D — Finders

New filters follow the existing `select*` pattern (`ShipFinder::selectClass()`, `WareFinder::selectGroup()`): each takes a string or the matching object, resolves it through the owning collection where one exists (an unknown ID throws, as `ShipClasses::getByID()` does), de-duplicates, and is applied in `isMatch()`. Multiple calls combine by one documented rule: filters on a single-valued attribute match any selected value (as `selectGroup()` and `selectClass()` do); filters on what an item has or can do match only items that satisfy all selected values (as `selectTag()` does).

| Finder method | Matches | Multiple calls | Reads |
|---|---|---|---|
| `WareFinder::selectProducedBy(string\|ProductionMethodDef $method)` | wares with a production of the method | any | `WareDef::getProductionMethodIDs()` |
| `WareFinder::selectUsingResource(string\|WareDef $ware)` | wares whose productions consume the ware (the reverse of `productions.resources`) | all | `WareDef::usesResource()` |
| `WareFinder::selectLicence(string $licenceID)` | wares restricted by the licence | any | `WareDef::getLicenceID()` (not validated: no licence collection, so an unknown ID yields no matches) |
| `WareFinder::selectIllegalFor(string\|FactionDef $faction)` | wares illegal for the faction | any | `WareDef::isIllegalFor()` |
| `WareFinder::selectTransportType(string $transportTypeID)` | wares with the transport type | any | `WareDef::getTransportTypeID()`; validated against `WareTransportTypes::idExists()` |
| `ShipFinder::selectPurpose(string $purposeID)` | (from Part B) | any | `getMacroProperties()->getPurposeID()` |
| `ShipFinder::selectThrusterSize(string\|ShipSize $size)` | ships by thruster size | any | `getMacroProperties()->getThrusterSizeID()` |
| `ShipFinder::selectCapturable(bool $capturable = true)` | capturable (or only uncapturable) ships | single value, last call wins | `getMacroProperties()->isCapturable()` |
| `ShipFinder::selectWithHangar(string\|ShipSize $size)` | ships whose hangar holds the dock size (capacity above 0) | all | `getMacroProperties()->getHangarCapacity()` |
| `ShipFinder::selectWithSoftware(string\|WareDef $ware)` | ships that can install the software ware (default or optional) | all | `getMacroProperties()->getSoftware()->isInstallable()` |

**Reverse resource lookup: scan, no index.** `selectUsingResource()` scans every ware's raw production records once per `getAll()`. The whole dataset is 4909 resource lines on 1869 wares, so a scan is a few thousand array lookups, and the scan builds no objects (see lazy hydration). A stored reverse key (for example `usedAsResourceBy` in `wares.json`) is rejected because it is derived data that can drift from `productions`, the same reason ware data is not copied into `ships.json`. A precomputed in-memory index on `WareDefs` is rejected for now because nothing repeats the lookup per request; it is the upgrade path if a consumer ever needs one lookup per ware across all wares (`getMacroIndex()` in `WareDefs` is the pattern to follow), and adding it would not change the finder's API.

## Rationale
- **Ships:** the Part A fields have a named consumer (the mod's `CargoSizeExtractor` / `AccelerationOverrideDef`). The steering curve and explosion damage are the next facts the mod reads from raw XML (`ShipXMLFile`), so extracting them now saves a second `ShipDef` change and regeneration later. The remaining Part B fields serve the library's stated purpose as the X4 items database (`AGENTS.md`): loadout and fleet tooling needs hangar capacity, drone capacity, software and thruster size, and `ShipFinder::selectPurpose()` gives `purposeID` an immediate in-library consumer.
- **Wares:** price, production and licence apply to every ware. `EngineDef`'s docblock already promises ware prices that do not exist. They belong on `WareDef`, where ships reach them through `getWare()` without duplication.
- **Owner fix:** the wares work must read DLC patches anyway to get DLC production methods. The same mechanism fixes the missing owners, a data defect the user would otherwise inherit in `usedBy`.
- **`ShipMacroProperties` grouping:** keeps the public constructor additive while stopping its growth. Moving parsing into `ShipMacroPropertiesExtractor` keeps `ShipsExtractor` an orchestrator.
- **Text codes for descriptions:** descriptions are stored as text codes, not English strings, because they are long (an English copy would bloat `wares.json`) and the 7 shipped language files can resolve them at runtime in any language.
- **The smaller ship flags** (capturability, prestige, boost timing, threat score, player-coverable) apply to few ships each, but they cost one line of parsing and one nullable field each in a reader this plan already writes. Leaving them out would mean another `ShipMacroProperties` change and regeneration later. Capturability matters to boarding tools (all 14 Kha'ak ships are uncapturable). The default loadout is the only equipment data the game defines for 20 ships, including the Kha'ak and the racers.
- **Production methods collection:** without it, `WareProduction::methodID` is an opaque string. The collection gives it a label, a "player can build" flag and default races. Its consumers are `WareProduction::getMethod()` and production tooling that must choose between recipes (for example `default` versus `terran`) and exclude methods the player cannot build (`isPlayerBuildable()`). Deferral was weighed (see Considered Alternatives): `methodID` stays stable either way, so deferring would be cheap, but the project's stated aim is a complete items database and the method data comes from the same `wares.xml` pass, so it is kept in this plan. The collection is justified by those consumers alone; `WaresPatchReader` already has its own consumer in the wares pass 2 and does not depend on it.
- **Public API surface:** only Part A, the ware data and the cargo helpers have a named consumer, so only they get `ShipDef` accessors. Part B accessors exist once, on `ShipMacroProperties`. Adding a delegator later is additive; removing one is a breaking change in a published package.
- **Illegal factions and the buy restriction:** `<illegal>` is the last unhandled child of the ware patches. Extracting it lets the patch pass treat every known child explicitly, keeping the "unknown child" notice for genuinely new data. The buy restriction is one boolean on 3 wares, read from an element the extractor already parses for the licence.
- **Volume and transport type:** `cargoCapacity` alone cannot answer "how many units of X fit in this ship"; volume per unit and the transport type can. Both are attributes the wares extractor already walks past, they exist on every ware, and the first consumer (the Cargo Sizes mod) needs them. They are stored as flat `WareDef` keys, not on ships, in line with the rule that ware data lives in `wares.json` only.
- **Finders:** a collection database is only as useful as the questions it answers cheaply. The new filters are one-line `isMatch()` additions over data this plan already extracts, so adding them now saves later consumers from scanning `getAll()` themselves. The reverse resource lookup ("what consumes silicon wafers?") is the one with the clearest need, because the data only stores the forward direction.
- **Lazy ware hydration:** `WareDefs` is the one collection every domain touches, so cost added to `WareDef::fromArray()` is paid by consumers that never read a production. Keeping the raw records and building objects on first access costs one cache field per lazy value and removes about 1700 production objects (and one price object per priced ware) from every cold start.
- **Translation fallback:** the shipped languages are complete today, but the sentinel `{page,id}` that `ts()` returns for a missing entry is the worst thing a UI can show. A single helper that falls back to English, then to an empty string, gives all four translatable accessors one behavior, and a real existence check replaces string comparison against the sentinel.
- **Production cost helper:** recipe choice is the stated consumer of production data, and "what do the inputs cost" is the first question it asks. The data supports it fully (every resource ware exists and has a price), so it is cheap to provide and honest to caveat.
- **Value types:** `ShipPurposes` is a constants class with `getIDs()`/`idExists()`. Its consumers are the extraction-time validation and `ShipFinder::selectPurpose()`. No speculative structure is introduced: every new class has one of the consumers above.

## Pattern Alignment
- Follows `WareDef::KEY_MACRO_ID` / `ModuleDef` / `EngineDef` for `macroID` / `getMacroID()` and `WareDef::getMacro()` for `MacroFileDef` accessors.
- Follows `ModuleDef::KEY_DRONE_CAPACITY` / `getDroneCapacity()` for `droneCapacity`.
- Follows `droneCapacity` / `cargoCapacity` naming (`…Capacity`) for `deployableCapacity` / `countermeasureCapacity`. **Departure:** the existing `storageMissile` key is not mirrored, because "storage" is ambiguous in X4; it stays unchanged for compatibility.
- Follows the flattening principle of the existing ship keys (`dragForward`, `jerkTravelAccel`, `accFactorForward`): one top-level key per value, prefixed by its concept.
- Follows `WareDef::toArray()` (omit optional keys when empty) for every nullable key, in both `ships.json` and `wares.json`.
- Follows `ShipSlotDefinition` (`src/X4/Database/Ships/Equipment/`) for nested value classes with `fromArray()`, and its sub-namespace convention for the new `Ships\MacroProperties\` folder.
- Follows `ModuleMacroExtractor` for the per-item macro reader.
- Follows `ShipFinder::selectClass()` for `selectPurpose()`, `selectThrusterSize()`, and (with the any/all rule described in Part D) the other new ship and ware finder methods; `ShipFinder::selectBuilderFaction()` for the faction-taking `selectIllegalFor()`; `WareFinder::selectTag()` for the match-all filters.
- Follows `ShipSizes` constants and the planned `ShipPurposes` for `WareTransportTypes`.
- Follows `WareDefs::getMacroIndex()` (`src/X4/Database/Wares/WareDefs.php`) as the pattern for any future precomputed lookup; none is added now.
- Follows the data-backed `FactionDefs` / `FactionsExtractor` collection pattern (`src/X4/Database/Factions/`) for `ProductionMethodDefs` / `ProductionMethodsExtractor`, including a `DatabaseBuilder` method and a composer script.
- Follows the console prefixes `WARNING | …` / `NOTICE | …` used by both extractors.
- Follows the test pattern of checking extractor output against raw XML and skipping when game data is absent (`ShipDefTests::test_cargoCapacity_isNeverZeroWhenStorageIsDeclared()`).
- **Departure:** readonly promoted constructor properties with named arguments in the new value classes. Existing classes use explicit private fields, but PHP `>=8.4` is required (`composer.json`). For classes whose whole purpose is to be immutable and safe to extend, readonly properties enforce that, and named arguments keep their constructors safe to grow.
- **Departure:** `WareDef` hydrates `WarePrice` / `WareProduction` lazily and keeps raw records, whereas every other item class (`ShipDef`, `ModuleDef`, `EngineDef`, and `WareDef` today) builds its fields in `fromArray()`. Justified in Rationale: `WareDefs` is loaded by every domain and carries about 1700 productions.
- **Departure:** descriptions are stored as text codes, while labels are stored as English strings. Justified in Rationale (size, localization).
- Changelog follows the WIP convention (`562238b`): `## vX.Y.Z - **WIP; UNRELEASED**` with `- Area: text.` bullets.

## Detailed Steps
1. **Capture the baselines (no dependencies; must run before any other step, and before any `composer test` run, because the extractor tests rewrite the data files).** Copy `data/wares.json` and `data/ships.json` to `%TEMP%\x4-core-baseline\wares.json` and `%TEMP%\x4-core-baseline\ships.json`. This is outside the repository, and the run does not clean it. Also record the load-cost baseline there, in the same step, because it cannot be recovered once the code has changed: run a throwaway PHP script from outside the repository that, in a fresh process each, calls `WareDefs::getInstance()->getAll()` and `ShipDefs::getInstance()->getAll()` three times and writes the median wall time and the peak memory (`memory_get_peak_usage(true)`) of each to `%TEMP%\x4-core-baseline\load-cost.json`. Step 13 consumes it.
2. **Fix the `WaresExtractor` namespace.** Change `src/X4/Database/Wares/WaresExtractor.php` to `namespace Mistralys\X4\Database\Wares;`. Update the imports in `src/X4/Database/DatabaseBuilder.php` L20, `src/X4/Database/Wares/WareDefs.php` L10 and `tests/X4Tests/Suites/Database/Extractors/WaresExtractorTests.php` L9. Add NEW `src/X4/Database/Wares/Legacy/WaresExtractor.php`, declaring `namespace Mistral\X4\Database\Wares; /** @deprecated */ class WaresExtractor extends \Mistralys\X4\Database\Wares\WaresExtractor {}`. Run `composer dump-autoload`.
3. **Ware value classes and `WareDef` extension.**
   - Add NEW `src/X4/Database/Wares/WarePrice.php`: final, readonly `min`, `average`, `max` (int), `fromArray()`, `toArray()`.

## Assumptions
- The extracted game data (v9.0.0.0) is present and matches the data used for the v1.4.1 regeneration.
- Only x4-core changes, so no cross-repository symlink switch is planned.
- `hasOwnAccFactors` is true for a partial `<accfactors>` element, because the mod's `<replace>` only needs the element to exist.
- Hangar bays with `hidden="1"` are not usable hangar space; none is referenced by a ship today.
- `<ownership playercoverable>` and `<restriction buy>` are exposed as raw flags; their in-game meaning is not documented in the game data and is not interpreted.
- The ware `transport` and `volume` attributes are not changed by any DLC patch (no `replace`/`remove` operation exists in any data folder, and the `<add>` patches carry only owners, productions and illegal factions).
- A ship can carry a ware when the ware's transport type is one of its `cargoType` tokens. The data shows matching vocabularies but does not state the rule; it is documented as derived.
- Production method `<default race>` values are race IDs, stored as given; they are not validated against `FactionDefs`, because races and factions are different concepts.

## Constraints
- Additive public API only: no change to existing constants, getter signatures or constructor positions. Existing JSON values change only for the corrected `factions` / `usedBy`.
- PHPDoc on all public classes and methods; synchronous file I/O; manifest docs updated with every code change (`docs/agents/project-manifest/constraints.md`, x4-core `AGENTS.md`).
- `composer dump-autoload` after adding classes.
- Data files use LF line endings (handled by `LineEndingNormalizer`).

## Out of Scope
- Migrating `x4-mod-cargo-sizes` to the new API (separate later plan).
- Any release action (see Human Actions).
- Ship macro `<effects>` and `<sounds>`: references to visual and audio assets with no gameplay value.
- Library-level loadout and spawning data (`libraries/loadouts.xml`, `loadoutrules.xml`, `ships.xml`, `shipgroups.xml`, `jobs.xml`): story, scenario and NPC spawning setups rather than ship properties; they need their own collections and a separate plan.
- Reshaping the 42-parameter `ShipDef` constructor or moving the existing stat parsers out of `ShipsExtractor`.
- Changing the pass-1 rule that drops a ware with an unknown owner faction.
- A `LicenceDefs` collection and extraction of the per-faction licence definitions in `libraries/factions.xml` (see Considered Alternatives and Deferred Items).
- Changing `TranslationDefs::t()` / `ts()` behavior for existing callers.

## Testing Strategy
- Unit tests for each new value class: serialization round trips, defaults and computed accessors.
- Accessor tests on `ShipDef` and `WareDef`.
- Extractor-output tests that compare the data files against an independent raw-XML scan for every ship or ware, skipping when game data is unavailable (the established `ShipDefTests` pattern).
- A patch-reader test against the real DLC files.
- Finder tests compare each new filter against an independent scan of the raw XML or the extracted data, and pin the any/all combination rule.
- Reflection-based tests pin the lazy-hydration contract (no value objects built on load; built once on first access) deterministically; load timing is a scripted step 13 comparison, not a PHPUnit test.
- Translation fallback is tested with a `Language` test double whose translator lacks the entry, because every shipped language is complete today.
- A one-off baseline diff (step 13) proves that the only pre-existing value changes are the intended owner corrections.

## Risks & Mitigations
| Risk | Mitigation |
|------|------------|
| **Regeneration silently changes existing values.** | Step 1 baselines and the step 13 diff allow only the enumerated owner corrections; anything else is investigated. |
| **Test runs overwrite the data files mid-run.** | Baselines are captured first (step 1); step 14 re-checks the data after `composer test`. |
| **The owner fix surprises consumers** (more factions in `usedBy`). | It is a correction verified against the game's own patches; the changelog names it explicitly. |
| **A future game update introduces `replace`/`remove` ware patches.** | `WaresPatchReader` warns on every unsupported operation; troubleshooting docs explain the follow-up. |
| **`cargoMacroID` disagrees with `cargoCapacity`** after the refactor. | Both come from one `ShipCargoInfo`; `test_cargoMacro_consistentWithCargo` cross-checks the raw XML. |
| **Hangar capacity is confused with dock counts.** | Distinct names, cross-referenced docblocks, a handbook section, and tests that pin both. |
| **The resolver's `WARNING` floods the console.** The previous dock-size path swallowed unresolved macros silently, and the resolver now walks every `<connection>` of every ship. | Step 13 checks the extraction output for unexpected resolver warnings; the fallback is to warn only on the `con_storage*` path and use `NOTICE` elsewhere. |
| **The dock-size refactor changes `equipment.docks`.** | It goes through the same resolver with identical first-match behavior; the step 13 diff covers `equipment`. |
| **Public constructor change breaks external `new ShipDef(...)` / `new WareDef(...)` callers.** | Only trailing optional parameters are added; the existing direct calls run unmodified. |
| **Nullable "override" fields are misread as capacities.** | `…Override` accessor names, PHPDoc stating that null means the game default, handbook text. |
| **Raw flags (`playerCoverable`, `buyRestricted`) are read as documented game rules.** | Raw names, PHPDoc and handbook text saying the meaning is unconfirmed; no derived behavior is built on them. |
| **Loadout equipment macros do not map to wares** (e.g. NPC-only Kha'ak equipment). | Items keep their macro ID and `getWare()` returns null; the ware is resolved at runtime, so nothing stale is stored. |
| **A DLC redefines an existing production method ID.** | Later data folder wins, with a `NOTICE`; the step 13 check pins the 12 expected methods. |
| **Deprecated namespace shim confuses static analysis.** | The shim is a one-line subclass annotated `@deprecated`; `composer analyze` runs in step 14. |
| **Lazy hydration leaks into behavior** (a cache field breaks equality or `toArray()`, or a finder accidentally hydrates). | The cache is private and `toArray()` serializes from the records; `test_hydration_isLazy` and `test_constructWithValueObjects_equalsRecords` pin both; the step 13 load-cost comparison catches a regression in practice. |
| **`WareDefs` cold load still grows** because `wares.json` is larger (volume, transport and records on 1869 wares). | The step 1 baseline and the step 13 comparison (within 2x); the decode cost of the extra keys is small next to object construction, which is what the lazy design removes. |
| **`canTransport()` is read as a game rule.** The data shows matching vocabularies, not an explicit compatibility statement; station modules are `container` wares too. | PHPDoc and handbook say the rule is derived and ignores trade rules; the method name says "can transport", not "can trade". |
| **Fallback hides a missing translation.** | The English text is the documented fallback and the raw code is never shown; the shipped languages are complete today (verified), so no current consumer sees a fallback. Missing entries in a future game version remain detectable through `Language::hasCode()`. |
| **Production cost is read as a market price or a profit.** | The PHPDoc and handbook name the basis (reference average price, inputs only, no effects or time) and the helper returns null instead of guessing when a price is missing. |
| **Finder combination rules surprise callers** (any versus all). | One rule, stated in the PHPDoc of every method and in the handbook, mirroring `selectGroup()` / `selectTag()`; tests pin both behaviors. |
| **The reverse resource scan becomes slow** if a consumer calls it once per ware. | Documented upgrade path: an in-memory index on `WareDefs` behind the same finder API, following `getMacroIndex()`; no stored key is added. |
| **Licence IDs stay opaque.** | The limitation is recorded in Deferred Items and the handbook; `selectLicence()` and `getLicenceID()` use the game's own type key, so a later collection is additive. |
